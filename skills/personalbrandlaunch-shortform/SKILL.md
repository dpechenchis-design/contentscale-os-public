# personalbrandlaunch-shortform — фреймворк Ava (@personalbrandlaunch)

Четвертий движок-фреймворк поряд з dan-martell-shortform / jason-cooperson-shortform /
hormozi-shortform. Джерело: скріншоти + транскрипти + аналіз останніх 20 reels, надані
Дариною 10.07.2026. Відрізняється тим, що це не лише скелет скрипта, а повна методологія
"як шукати й красти структуру" (Pillar 2 хука через 5X rule) + окрема бібліотека готових
скелетів, знайдених у неї в акаунті.

## ⚠️ ДЖЕРЕЛО ДАНИХ — жорстке правило

Усі рілсів для роботи беруться **ТІЛЬКИ з бази цього скіла**. Інших джерел немає.

- `references/reels-database.md` — 100 рілсів @personalbrandlaunch: посилання, дата, перегляди, лайки, коменти, фоловери і **повний дослівний транскрипт**. Відсортовано за переглядами.
- `references/reels-table.xlsx` — оригінальна таблиця (ті самі дані; картинки винесені в `visuals/`, щоб скіл важив мало).
- `references/visuals/<shortcode>.jpg` — скрін формату і хука на екрані (100 з 100). **Перед вибором рілса відкрий його скрін (Read) і подивись**: формат зйомки (talking head / split-screen / вулиця / BTS / текст на екрані), текст хука в кадрі. Формат у примітці ресогу пишеш за скріном, а не вгадуєш з транскрипту.

Правила:
1. Посилання, метрика, транскрипт — **копіюються з бази дослівно**. Не округлювати (4,549,912, не «4.5M»), не переказувати, не скорочувати транскрипт — ліва колонка ресогу = ВЕСЬ транскрипт, біт за бітом.
2. Не скрейпити і не шукати рілси інструментами (vidIQ тощо), не брати приклади «з пам'яті» — поки у базі є потрібне.
3. `BTS` / порожній транскрипт / пісня / не англійською = без мови креатора → для 1:1 ресогу не годиться (хіба скелет повністю в тексті на екрані — тоді дивись скрін).
4. Метрика — на дату вивантаження таблиці; у доці так і підписувати.
5. `references/viral-frameworks.md` / `framework.md` — для назв фреймворків і розуміння скелетів, **не** як джерело оригінального тексту.

## ⚠️ ПРАВИЛО 1:1 (жорстке, з правки Дарини 10.07.2026)
Скелети з `references/structure-templates.md` беруться **1:1 по структурі**, так само як
`viral-1to1-reskin.md` для 🟣 вірал-бакета: та сама послідовність рядків, той самий ритм,
той самий тип кожного рядка — міняються ТІЛЬКИ змінні під нішу/клієнта (тема, цифри, приклади).
НЕ «за мотивами», НЕ перефразований скелет власними словами. Якщо для якогось скелета немає
чіткого référence-відео від клієнта чи ніші — повернути картку з проханням дати референс,
а не вигадувати власну версію «в дусі» скелета. Чесність заявок (Проф/цифри/результати) —
той самий гейт, що й у інших трьох движках: підставлені факти мають бути правдою клієнта.

## Референси
- **framework.md** — 6 Pillars: Topic → Hook (5X rule) → Structure → Format → Value → CTA;
  Proof/Promise/Plan хук-формула; діагностичні "чому X перемагає Y" пости (CPS, сценарій vs
  фрістайл); 5 типів контенту → ціль.
- **structure-templates.md** — бібліотека скелетів (зростає з кожним новим прикладом від
  клієнта/ніші): Handwave, Picture+Name, Two-People, If-X-You-Y, Comparison A-vs-B,
  Hypothetical-Challenge. Кожен — з оригінальним прикладом + витягнутим скелетом-заготовкою.
- **production-formats.md** — бібліотека форматів ЗЙОМКИ (не хука/структури, а того, ЯК
  знято): з реальних client-facing скриптів іншого агентства (мультитаскінг, POV з рухом по
  сетингах, voiceover+broll монтаж, post-it note reveal, Q&A інтерв'юер/інтерв'юйований,
  viral-video-reaction green screen). Використовується для Pillar 4 (Format) і для поля
  "How to record it" у картці-пакеті script-factory.

## Скелет методології (6 Pillars)
1. **Topic** — тема/пілар контенту клієнта.
2. **Hook (перші 3с)** — знайти через **5X rule**: пошук у Reels tab по ніші, знайти відео
   з переглядами ≥5× середньої аудиторії того автора → взяти письмовий, вербальний і
   візуальний скелет хука.
3. **Structure** — обрати ОДИН скелет з `structure-templates.md` (1:1, див. правило вище).
4. **Format** — обрати ОДИН формат зйомки з `production-formats.md`.
5. **Value** — власна експертиза клієнта (НЕ з референсу).
6. **CTA** — follow-тип (ріст) або lead-тип (лід-магніт/продаж) — див. сегментацію нижче.

## Сегментовані CTA (знахідка з аналізу 20 reels — унікальна для цього движка)
Ava веде КІЛЬКА паралельних comment-keyword автоматизацій замість однієї CTA, розділяючи
аудиторію за наміром:
- **Контент-лід-магніт** (росту аудиторії): "HOOK" → 1000 шаблонів хуків, "STORY" →
  сторітелінг-шаблони. Для контенту, що вчить конкретному навику.
- **Продаж послуги** (реальні ліди): "SMM" → done-for-you агентство. Для POV/hypothetical-
  challenge контенту, де показується експертиза, а не роздається інструмент.
- **Позичена авторитетність**: ім'я/бренд ("Ava") → повний епізод подкасту — для нарізки
  чужого/власного довшого контенту.
Правило вибору: якщо відео вчить ЯК зробити щось самому — контент-лід-магніт CTA; якщо
відео демонструє експертизу БЕЗ повного розкриття методу (POV, hypothetical challenge,
day-in-life) — CTA на послугу.

## Якір проти сліпого копіювання (з аналізу 20 reels)
Особистий/діарі-контент (BTS, «тиждень із життя») — непослідовний перформер: топ-ролик
акаунту (666K, 19.3x) — особиста історія походження, але «Weekly Diary» відео отримало
негативні коментарі («той самий, репост»). Не копіювати особистий формат сліпо — тільки
якщо в клієнта справді є сильна оригінальна історія.

## Коли викликати
Пілар для 🟢 talking head / 🟣 вірал КОЛИ клієнт — сам обличчя свого бізнесу (коуч,
консультант, соло-експерт), що хоче зростання ОСОБИСТОГО бренду + лідогенерацію власних
послуг — не для суто розважальних/entertainment акаунтів. Порівняльний (A-vs-B) і
Hypothetical-Challenge скелети — це те, чого немає в dan-martell/cooperson/hormozi/
name.is.joao — обирати ЦЕЙ движок саме під ці два патерни, або коли потрібна сегментована
CTA-по-типу-контенту логіка.

## Режим: 1:1 Viral Reskin (два стовпці)

Коли команда дає конкретне віральне відео як референс, Claude виконує повний 1:1 реског замість генерації з 6 Pillars.

### Процес
1. Взяти рілс з `references/reels-database.md` (або той, що назвала команда, — теж шукати в базі): посилання, метрика і ДОСЛІВНИЙ повний транскрипт звідти. Подивитись його скрін у `references/visuals/`.
2. Розібрати скелет построково: кожен рядок = окремий біт (хук, приклад, число, CTA).
3. Переписати рядок-в-рядок, підставляючи змінні під клієнта: нішу, приклади, числа, CTA.
4. НЕ додавати / НЕ прибирати / НЕ міняти порядок бітів.

### Головне правило
**Віральний хук залишається 1:1.** Хук не змінюється — змінюється ТІЛЬКИ контекст під клієнта. Структура вже доведена переглядами; міняємо лише змінні (ніша, приклади, числа, CTA keyword).

### Формат виводу: шапка + таблиця з двох колонок

**Шапка (завжди перед таблицею):**
> **Референс:** [назва/опис відео](посилання на оригінал) | **Views:** X | **Likes:** X | **Creator:** @handle

| Original | Версія під клієнта |
|---|---|
| [біт 1 оригіналу дослівно] | [біт 1 під клієнта] |
| [біт 2 оригіналу дослівно] | [біт 2 під клієнта] |
| ... | ... |

Ліва колонка = дослівний транскрипт оригінального відео.
Права колонка = версія під клієнта, вирівняна біт-в-біт.
Посилання + метрика оригіналу завжди у шапці над таблицею.

### Гейти
- **Чесність:** кожна підставлена заявка = правда для клієнта зараз. Не присвоювати чужий результат.
- **On-topic ICP:** змінні з НІШІ клієнта, не тягти чужу тему.
- **ToV:** лексика клієнта, структура/ритм оригіналу не чіпаються.

### Контекст клієнта
Контекст (DNA, voice notes, ніша, ToV) надає ОКРЕМО людина з команди, яка працює зі своїм клієнтом. Цей скіл пояснює лише ПРОЦЕС адаптації.
