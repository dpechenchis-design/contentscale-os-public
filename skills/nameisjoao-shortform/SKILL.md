# nameisjoao-shortform — движок подачи мнения/инсайта (opinion-контент)

Когда у контент-менеджера есть ПОЗИЦИЯ/инсайт/хот-тейк, которым хотим поделиться — этот движок.
Не how-to (это Dan Martell/Sam/Hormozi), а «взять стойку и донести так, чтобы досмотрели и переслали».

## ⚠️ ДЖЕРЕЛО ДАНИХ — жорстке правило

Усі рілсів для роботи беруться **ТІЛЬКИ з бази цього скіла**. Інших джерел немає.

- `references/reels-database.md` — 100 рілсів @name.is.joao: посилання, дата, перегляди, лайки, коменти, фоловери і **повний дослівний транскрипт**. Відсортовано за переглядами.
- `references/reels-table.xlsx` — оригінальна таблиця (ті самі дані; картинки винесені в `visuals/`, щоб скіл важив мало).
- `references/visuals/<shortcode>.jpg` — скрін формату і хука на екрані (4 з 100). **Перед вибором рілса відкрий його скрін (Read) і подивись**: формат зйомки (talking head / split-screen / вулиця / BTS / текст на екрані), текст хука в кадрі. Формат у примітці ресогу пишеш за скріном, а не вгадуєш з транскрипту. У Joao **один формат на всі рілси**: селфі talking head крупним планом, хук у чорній плашці вгорі кадру. Тому скрінів 4 — вони еталон формату для всіх 100. Для решти рілсів формат = цей самий, текст хука в плашці = перший рядок транскрипту.

Правила:
1. Посилання, метрика, транскрипт — **копіюються з бази дослівно**. Не округлювати (4,549,912, не «4.5M»), не переказувати, не скорочувати транскрипт — ліва колонка ресогу = ВЕСЬ транскрипт, біт за бітом.
2. Не скрейпити і не шукати рілси інструментами (vidIQ тощо), не брати приклади «з пам'яті» — поки у базі є потрібне.
3. `BTS` / порожній транскрипт / пісня / не англійською = без мови креатора → для 1:1 ресогу не годиться (хіба скелет повністю в тексті на екрані — тоді дивись скрін).
4. Метрика — на дату вивантаження таблиці; у доці так і підписувати.
5. `references/viral-frameworks.md` / `framework.md` — для назв фреймворків і розуміння скелетів, **не** як джерело оригінального тексту.

## Референс
- **skeletons-S1-S7.md** — 7 скелетов (S1 Аксиома · S2 Rule+Reason с триадным рефреном · S3 Listicle-луп ·
  S4 Insider Deep-Dive · S5 Flip/Twist · S6 Validation · S7 Story-repost) + 3 механики виральности +
  CTA 3 уровней. Полный реверс его корпуса (~50 транскриптов).

## 3 механики виральности (переносятся в любую нишу — это КРАФТ)
1. **Команда-хук с открытой петлёй**: «Never trust a [X] who does this» — «this» не раскрыто → досматривают.
2. **Инсайдерская позиция**: «as a [insider] myself, and you're not going to like it» → сливаешь аудитории
   «что на самом деле думает другая сторона» (работодатель/клиент/рынок/алгоритм) → доверие.
3. **Идентичность + шер-триггер**: контент говорит за зрителя то, что он чувствует, но не сформулировал
   («это про меня» → сейв; «это про них» → шер). Прямой send-this-to CTA.

## Когда какой скелет (opinion-триггер → S)
- Резкая максима/аксиома ≤15с → S1
- Правило/заповедь с «I don't care how…» рефреном → S2
- «3 signs / 3 things» листикл → S3
- Слом глубокой веры через инсайдер-монолог другой стороны → **S4 Insider Deep-Dive** (самый сильный;
  = инсайдерский слот недели в bucket-planner)
- Переворот образа/ожидания → S5
- Снять вину / вдохновить-возвысить → S6
- Чужая история/цитата как соц.доказ → S7

## Гейты (правила системы поверх движка)
- **ToV поверх, не тон:** берём его КРАФТ (петля, рефрен, инсайдер-угол, эскалация «it gets worse»,
  панч-аксиома), но лексика/тон = ToV клиента. Его резкость («fuck no», «I don't care») — НЕ копировать
  дословно, если ToV клиента мягкий (у Дарины — мягкий).
- **Честность:** позиция должна быть тем, во что клиент реально верит; инсайдер-«секрет» — правдой.
- **On-topic:** тема из ниши клиента; из dating берём только СТРУКТУРУ (см. эталон-реског
  Downloads/Daryna_Reskin_ViralTrap.md — S4 пересажен в «алгоритм/контент»).
- **1:1 реског:** если есть конкретный виральный референс — полный реског (див. секцію нижче).

## Режим: 1:1 Viral Reskin (два стовпці)

Коли команда дає конкретне віральне відео як референс, Claude виконує повний 1:1 реског замість генерації зі скелетів S1-S7.

### Процес
1. Взяти рілс з `references/reels-database.md` (або той, що назвала команда, — теж шукати в базі): посилання, метрика і ДОСЛІВНИЙ повний транскрипт звідти. Подивитись його скрін у `references/visuals/`.
2. Розібрати скелет построково: кожен рядок = окремий біт (хук, приклад, число, CTA).
3. Переписати рядок-в-рядок, підставляючи змінні під клієнта: нішу, приклади, числа, CTA.
4. НЕ додавати / НЕ прибирати / НЕ міняти порядок бітів.

### Головне правило
**Віральний хук залишається 1:1.** Хук не змінюється — змінюється ТІЛЬКИ контекст під клієнта. Структура вже доведена переглядами; міняємо лише змінні (ніша, приклади, числа, CTA keyword).

### Формат виводу: шапка + таблиця з двох колонок

**Шапка (завжди перед таблицею):**
> **Референс:** [назва/опис відео](посилання на оригінал) | **Views:** X | **Likes:** X | **Creator:** @handle

| Original | Версія під клієнта |
|---|---|
| [біт 1 оригіналу дослівно] | [біт 1 під клієнта] |
| [біт 2 оригіналу дослівно] | [біт 2 під клієнта] |
| ... | ... |

Ліва колонка = дослівний транскрипт оригінального відео.
Права колонка = версія під клієнта, вирівняна біт-в-біт.
Посилання + метрика оригіналу завжди у шапці над таблицею.

### Гейти
- **Чесність:** кожна підставлена заявка = правда для клієнта зараз. Не присвоювати чужий результат.
- **On-topic ICP:** змінні з НІШІ клієнта, не тягти чужу тему.
- **ToV:** лексика клієнта, структура/ритм оригіналу не чіпаються.

### Контекст клієнта
Контекст (DNA, voice notes, ніша, ToV) надає ОКРЕМО людина з команди, яка працює зі своїм клієнтом. Цей скіл пояснює лише ПРОЦЕС адаптації.
